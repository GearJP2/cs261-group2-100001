## US1 — เข้าสู่ระบบและยืนยันบัญชีมหาวิทยาลัย (Login)

**Priority:** High • **Estimate:** 3 points

- **As a:** นักศึกษาของมหาวิทยาลัยธรรมศาสตร์ที่มีบัญชีผู้ใช้ของมหาวิทยาลัย
- **I want to:** เข้าสู่ระบบเว็บแอปพลิเคชันด้วยบัญชีที่ยืนยันตัวตนของมหาวิทยาลัยได้อย่างปลอดภัย และสามารถออกจากระบบได้
- **So that:** สามารถเข้าใช้งานระบบนัดหมายกิจกรรมตามสิทธิของนักศึกษา และมั่นใจได้ว่าผู้ร่วมกิจกรรมเป็นนักศึกษาตัวจริง ป้องกันความเสี่ยงจากคนนอก

### Acceptance Criteria ที่ทีมให้มา

**Scenario 1: เข้าสู่ระบบสำเร็จด้วยข้อมูลที่ถูกต้อง**

- **Given:** ผู้ใช้อยู่ที่หน้า Login และมีบัญชีมหาวิทยาลัยที่ถูกต้อง
- **When:** ผู้ใช้กรอก Username และ Password (หรือผ่านระบบยืนยันตัวตนที่กำหนด) ถูกต้องแล้วกดปุ่ม Login
- **Then:** ระบบตรวจสอบสิทธิ์ผ่าน บันทึก Session และพานักศึกษาเข้าสู่หน้าหลักของระบบได้สำเร็จ

**Scenario 2: เข้าสู่ระบบไม่สำเร็จเมื่อข้อมูลผิดพลาด**

- **Given:** ผู้ใช้อยู่ที่หน้า Login
- **When:** ผู้ใช้กรอก Username หรือ Password ไม่ถูกต้อง แล้วกด Login
- **Then:** ระบบแสดงข้อความแจ้งเตือนข้อผิดพลาด และไม่อนุญาตให้เข้าสู่ระบบจนกว่าจะกรอกใหม่ถูกต้อง

### กรณีทดสอบเพิ่มเติมที่เสนอให้ทีมรับรอง

Logout อยู่ใน I want แล้ว แต่ยังไม่มี Scenario แยก จึงเสนอรายละเอียดต่อไปนี้เพื่อให้ตรวจรับได้ครบ:

- **Logout:** เมื่อผู้ใช้ที่เข้าสู่ระบบกด Logout ระบบยกเลิก session ฝั่งเซิร์ฟเวอร์และกลับหน้า Login; request ใหม่จาก session เดิมเข้าหน้าหรือ API ที่ป้องกันไม่ได้ รวมถึงแท็บอื่น
- **สิทธิ์นักศึกษา:** เมื่อ provider ยืนยันตัวตนได้แต่ไม่มีหลักฐานสิทธิ์นักศึกษาตามเกณฑ์ที่ตกลง ระบบไม่สร้าง session ที่ใช้ฟีเจอร์นักศึกษาได้
- **Session expiry:** เมื่อ session หมดอายุ ต้องเข้าสู่ระบบใหม่ก่อนใช้ฟีเจอร์ที่ป้องกัน
- **Provider unavailable:** เมื่อระบบมหาวิทยาลัยไม่ตอบสนอง แสดงข้อความลองใหม่ภายหลังและไม่สร้าง session จากผลตรวจที่ไม่สมบูรณ์

### ข้อจำกัดและงานที่ต้องตรวจสอบ

ยังไม่ยืนยันว่ามหาวิทยาลัยเปิด protocol/API ใดให้โปรเจกต์ใช้ ต้องตรวจช่องทางที่ได้รับอนุญาตและหลักฐานสิทธิ์นักศึกษาก่อน implement หากใช้หน้า Login ของมหาวิทยาลัย ให้กรอก credentials ที่หน้านั้น ไม่สร้างฐานเก็บรหัสผ่านมหาวิทยาลัยในแอป

US1 ไม่รวมการสร้าง Party และ 3 points เป็น estimate ที่ทีมให้มา ไม่ใช่ผลประเมินว่าการเชื่อมระบบภายนอกพร้อมแล้ว ทดสอบด้วย mock ได้ระหว่างพัฒนา แต่ต้องระบุให้ชัดและยังไม่ถือว่าเชื่อมบัญชีมหาวิทยาลัยสำเร็จ

## US2 — ค้นหาและกรองกิจกรรม (Search)

**Priority:** Normal • **Estimate:** 3 points

- **As a:** นักศึกษาที่กำลังหาเพื่อนเล่นกีฬา
- **I want to:** ค้นหาและกรองปาร์ตี้ตามประเภทกีฬา วันเวลา และลักษณะสถานที่ (เช่น Badminton หรือ Basketball court)
- **So that:** เลือกกิจกรรมที่ตรงกับความสนใจและเวลาว่างได้สะดวก

### Acceptance Criteria ตามข้อมูลต้นทาง

**Scenario 1: ค้นหาและกรองได้ผลลัพธ์ถูกต้อง**

- **Given:** มีปาร์ตี้กีฬาหลากหลายประเภทในระบบ
- **When:** ผู้ใช้พิมพ์ค้นหาหรือเลือกชนิดกีฬาและประเภทสถานที่
- **Then:** แสดงเฉพาะปาร์ตี้ที่ตรงเงื่อนไข

**Scenario 2: ไม่พบปาร์ตี้**

- **Given:** ผู้ใช้อยู่หน้าค้นหากิจกรรม
- **When:** ค้นหากีฬาที่ไม่มีปาร์ตี้เปิดอยู่ขณะนั้น
- **Then:** แสดงข้อความไม่พบกิจกรรมที่ค้นหา

### การเชื่อมกับ task และประเด็นที่ต้องตกลง

งานเพิ่มเติมที่เสนอ: ระบุ date/time filter ให้ตรวจช่วงเวลาอย่างไร พร้อม pagination และนิยามประเภทสถานที่ก่อนออกแบบ schema/query

## US3 — เข้าร่วมปาร์ตี้ (Join)

**Priority:** High • **Estimate:** 5 points

- **As a:** นักศึกษาผู้เข้าร่วมกิจกรรม
- **I want to:** กดขอเข้าร่วมปาร์ตี้ที่สนใจ
- **So that:** ให้ระบบตรวจที่ว่างและเพิ่มชื่อเป็นสมาชิกโดยไม่เกินความจุ

### Acceptance Criteria ตามข้อมูลต้นทาง

**Scenario 1: เข้าร่วมเมื่อมีที่ว่าง — Scenario ต้นทาง**

- **Given:** ผู้ใช้อยู่ในปาร์ตี้ที่มีที่ว่างและยังไม่เริ่ม
- **When:** กดเข้าร่วม Party
- **Then:** ตรวจสิทธิ์ผ่าน Database Transaction เพิ่มผู้ใช้เป็นสมาชิก และลดจำนวนที่ว่าง

**Scenario 2: ป้องกัน Party เต็มหรือเข้าร่วมซ้ำ**

- **Given:** Party เต็มหรือผู้ใช้เป็นสมาชิกแล้ว
- **When:** ผู้ใช้พยายามเข้าร่วม
- **Then:** แจ้งเตือนและปฏิเสธ

### การเชื่อมกับ task และประเด็นที่ต้องตกลง

**AC ที่ต้องปรับให้ตรงกับ task ที่ตกลงไว้:** Scenario 1 ต้องบันทึก Pending โดยไม่เพิ่มสมาชิกและไม่ลดที่ว่าง แล้ว US10 เป็นผู้เพิ่มสมาชิกเมื่ออนุมัติ คำขอ Pending ซ้ำต้องไม่เพิ่มรายการ; คนละบัญชีขอที่ว่างสุดท้ายได้หลาย Pending แต่ตอนอนุมัติสำเร็จได้ไม่เกินความจุ ทดสอบการอนุมัติแข่งกันใน US10 ไม่ใช่ใช้ US3 จองที่ไว้ก่อน

## US4 — ถอนตัวจากปาร์ตี้ (Leave)

**Priority:** High • **Estimate:** 2 points

- **As a:** นักศึกษาธรรมศาสตร์ผู้เข้าร่วมกิจกรรม
- **I want to:** ถอนตัวจากปาร์ตี้ก่อนกิจกรรมเริ่ม
- **So that:** สละสิทธิ์และคืนที่ว่างให้ผู้อื่นอย่างถูกต้อง

### Acceptance Criteria ตามข้อมูลต้นทาง

**Scenario 1: ถอนตัวก่อนเริ่ม**

- **Given:** ผู้ใช้เป็นสมาชิกและกิจกรรมยังไม่เริ่ม
- **When:** กดถอนตัว
- **Then:** ลบสถานะสมาชิกและเพิ่มจำนวนที่ว่างกลับ

**Scenario 2: ห้ามถอนเมื่อเริ่มหรือจบแล้ว**

- **Given:** กิจกรรมเริ่มหรือเสร็จสิ้นแล้ว
- **When:** ผู้ใช้พยายามถอนตัว
- **Then:** แจ้งว่าไม่สามารถถอนตัวได้

### การเชื่อมกับ task และประเด็นที่ต้องตกลง

ตาม task ฉบับแก้: ยืนยันก่อนถอน ป้องกันคืนที่ว่างซ้ำ และใช้ transaction/Party lock ร่วมกับการอนุมัติ เมื่อเพิ่มแชทในอนาคตต้องเพิกถอนสิทธิ์ด้วย

## US5 — แนะนำผู้ใช้งานอื่น (Recommend Other Users)

**Priority:** Low / Bonus • **Estimate:** 5 points

- **As a:** ผู้ใช้ระบบหรือผู้จัดปาร์ตี้
- **I want to:** เห็นผู้ใช้อื่นที่สนใจกีฬาเดียวกันหรือเคยเล่นร่วมกัน
- **So that:** ชวนมาร่วมปาร์ตี้หรือสร้างกลุ่มกีฬาได้ง่ายขึ้น

### Acceptance Criteria ตามข้อมูลต้นทาง

**Scenario 1: แสดงรายชื่อแนะนำ**

- **Given:** ผู้ใช้อยู่หน้าหลักหรือหน้าสร้างปาร์ตี้
- **When:** ระบบประมวลผลความสนใจหรือประวัติการเล่นร่วมกัน
- **Then:** แสดง Recommended Users ได้ถูกต้อง

### การเชื่อมกับ task และประเด็นที่ต้องตกลง

ตาม task ฉบับแก้: ไม่แนะนำตัวเองหรือคนซ้ำ ส่งเฉพาะ public fields; ปุ่มเชิญเป็น dependency ของ US13 ไม่ใช่ต้องทำระบบเชิญใหม่ใน US5

## US6 — ดูรายชื่อสมาชิกในปาร์ตี้ (View Members)

**Priority:** Normal • **Estimate:** 2 points

- **As a:** ผู้ใช้งานหรือสมาชิกในปาร์ตี้
- **I want to:** ดูรายชื่อสมาชิกทั้งหมดรวมบทบาท Host
- **So that:** ทราบว่าใครเข้าร่วมก่อนเวลานัดหมาย

### Acceptance Criteria ตามข้อมูลต้นทาง

**Scenario 1: แสดงสมาชิกครบ**

- **Given:** ผู้ใช้เปิด Party ที่มีสมาชิก
- **When:** ระบบโหลดรายละเอียด Party
- **Then:** แสดงสมาชิกและบทบาท Host/Member ถูกต้อง

### การเชื่อมกับ task และประเด็นที่ต้องตกลง

ตาม task ฉบับแก้: แสดงเฉพาะสมาชิกปัจจุบันที่อนุมัติแล้ว ไม่รวม Pending/Rejected/ผู้ถอนตัว และอัปเดตหลังอนุมัติหรือถอนตัว

## US7 — สร้าง แก้ไขและยกเลิกปาร์ตี้ (Create / Edit / Cancel Party)

**Priority:** High • **Estimate เดิม:** 8 points — ต้องประเมินใหม่เมื่อรวมสร้าง Party (ยืนยัน scope 2026-10-17)

- **As a:** นักศึกษาที่เข้าสู่ระบบด้วยบัญชีมหาวิทยาลัยและบัญชียังใช้งานได้
- **I want to:** สร้างปาร์ตี้กีฬา และแก้ไขรายละเอียดหรือยกเลิกปาร์ตี้ที่ตนเป็น Host
- **So that:** นัดหมายกิจกรรมกับผู้อื่น และจัดการนัดหมายได้เมื่อแผนเปลี่ยน

### Acceptance Criteria

**Scenario 1: สร้าง Party สำเร็จ**

- **Given:** ผู้ใช้เข้าสู่ระบบและอยู่ในหน้าสร้าง Party
- **When:** กรอกชื่อ คำอธิบาย กีฬา สนาม เวลาเริ่ม–สิ้นสุดในอนาคต และความจุที่ถูกต้องแล้วกดสร้าง
- **Then:** Backend ตรวจช่วงเปิดสนามด้วย US9 สร้าง Party และ active Host membership ใน transaction เดียว ตั้ง Host จาก session และคืน `201`; หน้าเว็บพาไปหน้ารายละเอียด Party ใหม่ ผู้สร้างนับเป็นสมาชิก 1 คน จึงเหลือ `capacity - 1` ที่

**Scenario 2: ปฏิเสธการสร้างด้วยข้อมูลผิดหรือไม่มีสิทธิ์**

- **Given:** ผู้ใช้ส่งคำขอสร้างผ่านหน้าจอหรือ API โดยตรง
- **When:** ไม่ login, บัญชี inactive, ส่ง host_id เอง, ขาดข้อมูลจำเป็น, capacity ไม่ใช่จำนวนเต็มบวก, เวลาไม่อยู่ในอนาคต/สิ้นสุดก่อนเริ่ม, สนาม inactive/ไม่รองรับกีฬา หรือช่วงเวลาไม่เปิด
- **Then:** ปฏิเสธตาม error contract และไม่สร้าง Party หรือ Host membership ค้าง; หน้าเว็บคงค่าฟอร์มและแสดงข้อผิดพลาด

**Scenario 3: Host แก้ไขสำเร็จ**

- **Given:** ผู้ใช้เป็น Host และ Party ยังไม่เริ่มและยังไม่ถูกยกเลิก
- **When:** แก้ข้อมูลที่อนุญาตและกดบันทึก
- **Then:** ตรวจข้อมูลรวมกับค่าเดิม รวมถึงช่วงเปิดสนามและ capacity ไม่น้อยกว่าสมาชิก active แล้วบันทึก

**Scenario 4: ผู้ไม่ใช่ Host จัดการ Party ไม่ได้**

- **Given:** ผู้ใช้เป็น Member หรือ outsider
- **When:** พยายามแก้ไขหรือยกเลิก รวมถึงเรียก API ตรง
- **Then:** Backend ปฏิเสธและข้อมูลไม่เปลี่ยน

**Scenario 5: Host ยกเลิก Party**

- **Given:** ผู้ใช้เป็น Host และ Party ยังไม่เริ่ม
- **When:** ยืนยันยกเลิก
- **Then:** บันทึก cancelled_at หยุดรับคำขอใหม่ เก็บ membership/request เป็นประวัติ; ยกเลิกซ้ำคืน cancelled_at เดิม หากปิด dialog โดยไม่ยืนยันจะไม่ส่งคำขอ

### การเชื่อมกับ task

US7 รวมหน้าสร้างและ API สร้าง Party แล้ว ใช้ session จาก US1, schema จาก BASE-02 และตัวเลือกสนาม/ตัวตรวจเวลาจาก US9; กอล์ฟ + พีดู Backend, วี + เนทดู UI, โกลตรวจข้อมูล, ออสติน + กอล์ฟทดสอบ

## US14 — ให้คะแนนและรีวิวหลังจบกิจกรรม (Rate & Review Members)

**Priority:** Low • **Estimate:** 5 points

- **As a:** สมาชิกที่ร่วมกิจกรรมเสร็จแล้ว
- **I want to:** ให้ดาว รีวิว และรายงานพฤติกรรม เช่น No-show
- **So that:** สะสมคะแนนและความประพฤติไว้ประกอบการตัดสินใจ

### Acceptance Criteria ตามข้อมูลต้นทาง

**Scenario 1: ให้คะแนนหลังจบ**

- **Given:** Party สิ้นสุดและเป็น Completed
- **When:** ผู้ใช้ให้ดาว 1–5 และบันทึกรีวิวเพื่อนร่วมทีม

- **When:** สมาชิกไม่ซ้ำรายงานจนถึงเกณฑ์ เช่นเกินครึ่ง Party
- **Then:** หักเครดิตความประพฤติอัตโนมัติ

### การเชื่อมกับ task และประเด็นที่ต้องตกลง

AC ต้องปรับตาม task ฉบับแก้: แยก average_rating ออกจาก conduct_credit; คะแนนดาวเฉลี่ยไม่ใช่สูตรหักเครดิต ให้รีวิวเฉพาะสมาชิกกิจกรรมเดียวกันหลังจบ ห้ามตัวเอง/ซ้ำ กำหนดฐานนับผู้รายงานและเครดิตที่หัก แล้วหักได้ครั้งเดียวต่อคนต่อกิจกรรม
